# 初期版の技術選定

選定日: 2026-10-27（日本時間）。React + TypeScript + Viteによる架空データの試作品を実装済み。収集処理・Hono・D1は未実装で、Cloudflareには未公開。この文書は採用方針を示し、検証結果と残作業は [TODO.md](TODO.md) に記録する。

## 採用する構成

| 用途 | 選定 | 理由 |
| --- | --- | --- |
| UI | React + TypeScript + Vite + CSS | 検索結果、非表示設定、保存状態、インポート確認の状態をコンポーネントで管理する。ブラウザ内で動かし、SSRは初期要件に含めない |
| 配信 | Cloudflare Workers Static Assets / Workers Free | 画面・JS・商品JSONを静的配信できる |
| 商品検索 | ブラウザ内の文字列検索 | 入力ごとのAPI・D1読み取りを発生させない。正規化方式は明記する |
| 個人の非表示設定 | localStorage + バージョン付きJSON移行 | 認証基盤なしで試せる。端末間の自動同期は行わない |
| 商品取得 | 管理者のPCで動かすNode.js/TypeScriptスクリプト | 少数ページの検証から始められ、WorkerのCPU制限と分離できる |
| 商品配布 | 検証済みのJSONを静的アセットとしてデプロイ | 閲覧数が増えても商品DBへのクエリは増えない |
| 商品管理DB | 初期は不要。差分管理が必要になったらD1を1個追加 | 収集状態・変更の管理に限定して無料枠を使う |
| HTTP API | 必要になった段階でWorkers上のHonoを採用 | ルーティング、共通処理、エラー応答を整理する。初期の静的JSON配信には不要 |

初期依存はReact、React DOM、Vite、TypeScript、ViteのReactプラグイン、対応する型定義、Wranglerを中心にする。実装時に互換性を確認してバージョンを固定する。Next.js、ORM、KV、R2、Queues、Durable Objects、ログインは初期要件に含めない。HonoはHTTP APIの追加時に導入する。HTMLパーサーは取得元を検証後、必要なものを1つ選ぶ。

Reactは一覧・検索条件・非表示設定・インポート確認などの状態を連動させやすくするために採用する。配信するJSと依存は増えるため、端末で読み込みと操作性を確認する。状態管理はまずReact標準の機能と用途別のカスタムフックで行い、外部の状態管理ライブラリやルーターは必要になるまで追加しない。

Reactの採用だけでWorkerやD1の呼び出しを増やさない。Hono導入後も静的アセットの直接配信を維持し、動的処理は必要なAPIパスに限定する。Honoの採用とD1の採用はそれぞれ必要性を判断する。

```text
架空のサンプル / 検証後のBOOTH公開ページ
  → 管理用の取得・検証スクリプト
  → 正規化JSON（必要になればD1で差分を管理してから出力）
  → ローカルビルド・検証・Wranglerによる静的アセットのデプロイ
  → ブラウザで検索・非表示
                         ↔ localStorage / JSONファイル
```

D1への書き込みだけでは公開JSONは更新されない。更新手順にはJSON生成・検証・静的アセットの再デプロイまで含める。初期は管理者による手動更新とし、常時動作PCやCIの無料枠を前提にしない。更新頻度が必要になってから自動化を検討する。

## Workers / D1無料枠

2026-10-27に確認した公式値。上限と本プロジェクトの運用予算は別物。

| 項目 | Workers Freeの公式枠 | このプロジェクトの方針 |
| --- | --- | --- |
| 静的アセットへのリクエスト | 無料・回数無制限 | HTML/CSS/JS/JSONを直接配信する |
| Workerスクリプトのリクエスト | 100,000回/日 | 通常閲覧では起動させない |
| Worker CPU | HTTP・Cronとも1呼び出し10ms | 収集・大きなJSON生成はローカルで行う |
| 静的アセット | 20,000ファイル、1ファイル25MiBまで | JSON容量は下記の小さい試作予算で管理 |
| D1読み取り | 5,000,000行/日 | 導入時はプロジェクト予算500,000行/日 |
| D1書き込み | 100,000行/日 | 導入時はプロジェクト予算10,000行/日 |
| D1容量 | アカウント合計5GB、1DBあたり500MB | 1DB、100MBを見直し開始の目安にする |

D1の日次枠は日本時間09:00（UTC 00:00）でリセットされる。日次読み書き枠に達するとクエリがエラーになり、容量上限では書き込み等が制限される。無料プランで使い、枠超過時に自動で有料化する設計にしない。別プロジェクトとの枠の共有を確認する。

上記プロジェクト予算は安全なBOOTH取得頻度を意味しない。DB・配信の予算と取得元への負荷は別々に検証する。無料枠内での運用はデータ量・計測結果・アカウントの他用途を条件とし、将来の費用ゼロを保証しない。

## D1を使う場合の設計と試算

D1は商品メタデータの管理用とする。利用者の非表示操作・検索語・アクセスログを保存しない。ブラウザへCloudflareの認証情報を渡さず、管理用スクリプトから最小権限の認証情報でWrangler等を使う。公開書き込みAPIは作らない。

- 商品IDを主キーにし、表示名とは別に取得元で確認できたショップ識別子を保持する。ショップのサブドメインを使う場合は変更に弱いことを記録する。
- 価格は取得できた表示・通貨・範囲を保持し、不明を0円と扱わない。`fetchedAt`、`firstSeenAt`、確認できた場合のみ `publishedAt` を分ける。
- 内容のハッシュ等で差分を判定し、変更のない商品の無条件UPDATEを避ける。更新実行単位の記録と商品内容を分け、観測日時を毎回全商品へ書き込む必要性を検討する。
- SQLはパラメーター化し、主キーでの照合を中心に必要な索引だけ作る。商品本文・画像・取得HTML・無期限の履歴は保存しない。
- D1からは管理用スクリプトで分割読み出ししてJSONを生成する。途中失敗した出力は公開しない。

仮の規模を「管理対象5,000商品、1日1回のJSON生成、変更100商品/日」と置く。これは実際のカテゴリ件数や取得頻度の決定ではない。

| 処理 | 概算 |
| --- | --- |
| JSON生成の全件読み取り | 約5,000行/日 |
| 全件の差分照合 | さらに約5,000行/日（実行方式による） |
| 変更書き込み | 100商品 × 仮に本体・索引の計3行 = 約300行/日 |
| 初回登録 | 5,000商品 × 仮に計3行 = 約15,000行。日常予算を超えるため日を分ける等の投入計画が必要 |
| 容量 | 1商品2KBなら本体約10MB。索引・管理情報は別途実測 |
| 一般利用者の閲覧・検索 | D1読み書き0行 |

索引数・照合・削除・マイグレーション・管理操作・再試行で実際の行数は変わる。`meta.rows_read` / `meta.rows_written` とダッシュボードの使用量を記録し、実行前に残り予算を見積もる。大きな処理は分割し、予算接近時は次の処理を開始しない。停止中も最後の正常な静的データを配信する。

比較として、5,000商品を検索のたびに全走査すると、1,000回/日で500万行に達する。`LIMIT` を付けても走査行数が少なくなるとは限らず、部分一致の `LIKE '%語%'` に通常の索引が効くとは仮定しない。このため検索API＋D1を初期採用しない。Worker内キャッシュが命中してもWorkerのリクエストは消えないため、無料枠の根拠をキャッシュ命中率に置かない。

## データ配信と表示の予算

まずは最大5,000商品・非圧縮JSON合計5MiBを試作の検証目安とする。BOOTHの実件数は未測定。超える場合は黙って切り捨てず、収集範囲を明示して分割配信・検索方式を見直す。iPhone/iPadで読み込み・メモリ・検索時間を確認するまでは実用性を断定しない。

- JSONに形式バージョン、サンプル/実データの区別、収集元URL、収集範囲、成功した取得時刻を含める。
- データは世代付きファイル名、参照先を示す小さなmanifestは再検証するキャッシュ設定にする。1回の画面読み込みでは同一世代を使い、更新中のデータを混在させない。
- 初期の一覧はページ単位で描画し、数千枚のカードを一度にDOMへ追加しない。
- 「新着順」は取得元の新着一覧の順序を確認できた範囲で扱う。商品IDや初回観測日時だけで新着と断定しない。
- 商品サムネイルは表示を目標とし、取得・外部表示・保存の条件を確認するまでは仮画像のモックで設計を進める。説明全文は初期配信に含めない。検討状況は [sharing-and-thumbnails.md](sharing-and-thumbnails.md) を参照する。
- 全パスの `run_worker_first` を使わず、JSONの存在しないURLでHTMLを返すSPAフォールバックにも注意する。取得側はContent-Type・構造を検証する。

## 実装順と未検証事項

1. React + TypeScript + Viteで画面を作り、架空サンプルで検索、商品/ショップ非表示、解除、保存、JSON移行を実装する。
2. インポート不正・重複・置換確認・保存失敗、空結果・JSON取得失敗とPC/スマートフォン幅を検証する。
3. BOOTHの対象カテゴリURL、公開範囲、HTML、ページ送り、新着順、商品/ショップ識別子を少数ページで確認する。403/429では停止し、制限を回避しない。通常のCIテストには実BOOTHへの取得を含めない。
4. 最新の規約とデータ利用条件を照合し、取得範囲・停止条件・更新方針・掲載停止の連絡窓口を整えて実データを配信する。
5. 手動更新が負担になった場合にD1・自動収集を検討する。Cronを使うならFreeの10ms CPU枠内に収まる単位へ分割して計測する。定期収集だけでStatic Assetsが書き換わるとは扱わない。

ブラウザからBOOTHへのCORS、実際のカテゴリ件数、ページごとの取得可否、ショップIDの安定性、実機Safariでの挙動は未検証。BOOTHの認証情報や購入履歴は扱わない。
